# 判定: **条件付き GO**（B1〜B5 を設計に反映してから実装着手／再設計は不要）

全体として、この設計は「新しいテーブル・インデックス・依存・常駐プロセスを足さない」「既存の `query_relay`・チャンネル購読・`onOpenSearchResult` を再利用する」という点で、必要十分に保守的です。**プラットフォームの作り直しは不要**で、指摘はすべて局所修正で閉じます。ただし、**ページングと述語の適用順序**、**root 判定**、**リレー公開鍵の出どころ**に、受け入れ条件を静かに破る穴があります。

## Blocking findings

### B1. 絞り込みが LIMIT の後に来ると、ページングが壊れる（High）

**場所**: 提案1（`store/thread_flags.rs`）

**根拠**: ブリーフは「canonical distinct flags」「limit+1 probe」「返却済みの最終行でカーソルを取る」とありますが、**フラグ判定・モード判定・`q` 判定をどこで評価するか**が書かれていません。reactions を LEFT JOIN すると 1 スレッドが複数行に増えるので、素直に書くと (a) 行が重複する、(b) LIMIT がスレッドの途中で切れてフラグが欠ける、(c) Rust 側で後段フィルタすると `has_more` と `next_cursor` が実態とずれて**行が黙って消える**、のいずれかになります。受け入れ条件の「同一秒でもページ間で取りこぼさない」はこれで崩れます。

**修正**:
- root イベントで GROUP BY し、フラグは集約、モード判定は HAVING、`q` は WHERE に置く。**その後に** `ORDER BY created_at DESC, id ASC` → `LIMIT n+1`。Rust 側の後段フィルタは一切禁止（この一文を Issue に書く）。
- キーセット述語は `(created_at < :t) OR (created_at = :t AND id > :i)` と明示する。時刻 DESC・ID ASC の**向きが混在している**ため、`(created_at, id) < (:t, :i)` のような行比較で書くと必ず壊れます。ここが本 PR で一番危険な 1 行です。
- **(b) プランはリアクション駆動にする**。全モード（`all` 含む）が「フラグが 1 つ以上ある」を前提とするので、候補集合はメッセージ総数ではなくリアクション数で抑えられます。`LEFT JOIN reactions … HAVING count(*)>0` ではなく **EXISTS / INNER** で書くこと。これが効いていれば「新規インデックスなし」と `ILIKE '%q%'` の全文スキャン懸念が両立します（効いていなければ、`q` 検索はチャンネル履歴の逐次走査になります）。

### B2. `depth IS NULL` を root 扱いするのは、メタデータ未投入の返信を root に昇格させる（High）

**場所**: 提案1（thread_metadata を LEFT JOIN、`depth null/0`）

**根拠**: LEFT JOIN で「depth が NULL または 0」を root とすると、**thread_metadata 行がまだ無い返信**と、本物の root が区別できません。既存経路が repair しているのはチャンネル認可のキャッシュであって、thread_metadata ではありません。受け入れ条件「root kind9 のみ」に直接違反します。

**修正**: kind9 全件に対する thread_metadata の backfill が**全域で保証されているか**を実装前に確認する。保証されていないなら、イベント自身の返信マーカー（`e` タグの root/reply マーカー）を fallback にするか、メタデータ欠落を「root ではない」側に倒す。**メタデータ行を持たない返信**のテストを 1 本追加。

### B3. `coordinate` / `progress` と「完了が優先」の関係が未定義（Medium・仕様ブロッカー）

**根拠**: 「Completed overrides active visibility」は `active` に対してしか定義されていません。完了済みで🚩も付いているスレッドが `coordinate` に出るのかどうかで、SQL の述語もテストの期待値も変わります。

**修正**: `coordinate` = 🚩 かつ ☑️なし / `progress` = 🔴 かつ ☑️なし / `complete` = ☑️ / `all` = いずれか、と定義して Issue に明記。実装前に確定させる。

### B4. リレー公開鍵の出どころが「応答側」だと、署名検証が飾りになる（Medium〜High・セキュリティ）

**場所**: 提案3（「Trust pinned current relay public key as for existing overlays; investigate key lookup before implementation」）

**根拠**: ここが未調査のまま残っています。公開鍵を接続先の NIP-11 やハンドシェイク応答から取っている場合、オーバーレイの署名検証は「送ってきた本人が送ってきたことを確認する」だけになり、**偽装オーバーレイを弾けません**。ピン留めホスト `base813bbd…` があるのは良い兆候ですが、鍵のピン留めとは別物です。

**修正**: 39005/39006 と**同一の設定由来（out-of-band にピン留めされた）公開鍵**と一致することを表明的に検証し、その比較を既存の relay フェンスの内側で行う。応答から導出しない。あわせて **39007 の `d` タグ規約を 39005/39006 に合わせる**（3xxxx は addressable なので、フィルタ／カーソル違いの応答が同一座標になるとクライアント側キャッシュで取り違えが起きます）。

### B5. 新ブランチの差し込み位置が「認可キャッシュの repair」より前だと、失効チャンネルが通る（Medium・セキュリティ）

**根拠**: 既存経路は「NIP-98 → テナント所属 → キャッシュ済みチャンネル認可 **＋ repair**」を query 拡張の前に行う、とあります。新拡張は「existing auth の後」とだけ書かれており、**auth と repair の間**に入ると、失効済みチャンネルの温かいキャッシュで通過し得ます。

**修正**: repair の後ろに置くことを明記。既存のレート制限が新ブランチにも掛かることを確認（早期分岐で迂回しがち）。テスト: 「失効済みチャンネル＋キャッシュ温存」で拒否されること。

## 複雑さについて

**削れる候補は 1 つだけ**: フィルタ 5 モード（active/coordinate/progress/complete/all）。受け入れ条件が要求しているのは「active 一覧」「完了が検索できる」「3 種のフラグが見える」までで、`coordinate` / `progress` は必須ではありません。ただし B1 のとおり**クライアント側フィルタに逃がすことは不可**（LIMIT 後の絞り込みになるため）なので、残すならサーバ側です。

判断基準: **モード→述語のマップ 1 枚**で実装できるなら 5 モードは実質ゼロコストなので残す。5 本の SQL 文字列に分岐するなら `active` / `complete` / `all` の 3 つに削る。

それ以外（新テーブルなし・新インデックスなし・新デーモンなし・新 npm 依存なし・既存購読の再利用・シングルトンキャッシュや永続化を持たない・スナップショットデモ据え置き）は、**過剰でも過少でもありません**。特に「古いリレーでオーバーレイが無い場合は、空ではなく明示的な unsupported」は正しい設計判断です。

## テストへの追加（提案5 に対して）

不足しているもの:

1. **有効なオーバーレイ＋ rows 空**（= unsupported と区別できること）。これが無いと B4/「never silently empty」が検証されません

7. 返信へのリアクションが root を光らせない（N6）
8. 想定より新しい protocol version（N4）

ライブ状態の並行性テストは過剰なので不要です。
